# Qwen3.8-Flash-Next 177B 本地部署实录：RTX 5090 笔记本（24G 显存 + 64G 内存）跑出 256K 上下文与 23–28 tok/s

**English title:** Running Qwen3.8-Flash-Next 177B Locally on an RTX 5090 Laptop (24 GB VRAM + 64 GB RAM) — Quant Selection, Three-Tier Memory Split, and 256K Context

> 硬件：RTX 5090 Laptop GPU（24 GB 显存）/ 64 GB 内存 / NVMe 固态
> 目标模型：Qwen3.8-Flash-Next 的 GGUF 量化版（总参数 176.9B，其中 **51.2B 是 N-gram embedding 表**，MoE 主体 125.7B，激活约 3B）
> 最终成果：**生成 21~28 tok/s（社区同款配置基线约 11 tok/s），上下文从 8K 拉到 256K 全长**（256K = 262,144 tokens，即模型 `context_length` 标称值）
> 日期：2026 年 9 月

---

## 一、为什么这是个有意思的挑战

Qwen3.8-Flash-Next 是个"混合怪胎"：总参数 176.9B 的 MoE 模型，但里面有 **51.2B 参数是一张 N-gram embedding 表**（为投机解码和多 token 预测服务），另有 48 层 MoE 主体（512 个专家选 10 个）加 GatedDeltaNet 混合注意力。

对本地部署来说，这意味着一个残酷的数学题：

```
模型总量 ≈ 88 GiB（4.27bpw 量化）
显存 24 GiB + 内存 64 GiB = 88 GiB    ← 刚好等于模型大小，一 GiB 都不能浪费
```

也就是说：**任何一个字节的分配失误，都会让系统跌进页面交换的深渊**。但同时它又给了我们一个机会——这个模型的三大部分（N-gram 表 / 专家权重 / 注意力）访问模式完全不同，理论上可以各得其所：

| 部分 | 访问模式 | 理想存放位置 |
|---|---|---|
| N-gram 表（35.76 GiB） | 每 token 只查 16 行 ≈ 几 KB | **SSD**，mmap 按需分页 |
| 专家权重（每层 ~1 GiB，每 token 激活 10/512） | 每 token 每层都读激活的那几个 | **显存优先**，装不下的进内存 |
| 注意力 / 常驻张量 / KV | 每次都全读 | 显存 |

这套"三层分配"能不能成立，取决于一个此前被忽视的细节：**GGUF 分片布局**。这也是整个选型过程中最大的意外收获。

## 二、量化版本选型：三轮筛除，布局比特宽更重要

市面上能找到的量化版主要来自两家：**AtomicChat**（AD 系列）和 **unsloth**（UD 系列）。候选池一共 5 个：

| 候选 | 总大小 | 分片结构 | N-gram 表位置 |
|---|---|---|---|
| AtomicChat AD-5.00bpw-Q5_K_M-M64 | 102.93 GiB | 33 片 | **独占分片**（50.66 GiB，8.5bpw） |
| AtomicChat AD-4.27bpw-Q4_K_M-M64 | 88.03 GiB | 33 片 | **独占分片**（35.76 GiB，Q5_1 6bpw） |
| AtomicChat AD-3.84bpw-IQ4_XS-M64 | 79.10 GiB | 28 片 | **独占分片**（35.76 GiB，同上） |
| unsloth UD-IQ4_XS | 87.25 GiB | 3 片（0.01 / 46.41 / 40.83） | **混装**（IQ4_NL ≈26.8 GiB 与专家同片） |
| unsloth UD-Q3_K_XL | 83.80 GiB | 3 片（0.01 / 46.55 / 37.25） | 推定混装 |

### 第一轮筛除：unsloth 出局（布局问题，与位宽无关）

unsloth 的 3 分片把 N-gram 表和专家权重**混在同一个 46 GiB 分片里**。这在 128 GB 内存的机器上无所谓（全塞得下），但在 24G+64G 的机器上是致命的：

- 只要该分片里有任何一个张量被分配到显存，**整个 46 GiB 映射区域会被锁进内存**（无法换出），加上其他部分最坏要 89.6 GiB 常驻——直接爆内存；
- 想避免锁死，就只能把全部专家放 CPU，放弃显存分层，速度退回基线。

**教训一：在这类"模型比内存大"的部署里，分片布局比特宽重要得多。** unsloth 的默认布局是为 128 GB 统一内存/大内存机器设计的。

### 第二轮：AD 系列内部，4.27bpw 定主力

AD 系列三个档位共享同一张 6bpw 的 N-gram 表，差别在主体量化和表大小：

| 档位 | 主体大小 | 主体 bpw | 质量指标 |
|---|---|---|---|
| 5.00bpw | 51.6 GiB | 3.57 | — |
| **4.27bpw** | 51.6 GiB | **3.57** | **KLD 0.0842 / Top-1 89.49%（发布方实测）** |
| 3.84bpw | 42.7 GiB | ≈2.92 | 无数据 |

4.27 和 5.00 的主体完全相同（3.57bpw），只差表的量化；3.84 的主体被压到 ≈2.92bpw，速度会更快但质量没有公开数据背书。**主力选 4.27**（有 KLD 实测），3.84 后来补下载做了速度对照（见第六节）。

### 第三轮：NVFP4 为什么不在候选里

RTX 5090 是 Blackwell，原生支持 NVFP4 张量核，所以"要不要上 FP4"是个自然问题。结论是不采用，三层原因：

1. **没有这个版本** —— 两个发布方的仓库全量枚举（AtomicChat 104 个文件 + unsloth 60 个文件），量化档位只有 K-quant / I-quant 系列，`fp4` / `nvfp` 关键字零命中；
2. **瓶颈不在算力** —— NVFP4 加速的是矩阵乘法，而本机生成阶段的瓶颈是内存带宽（每 token 读一遍激活的专家权重，实测约 20~25 GB/s 打满），算力从来不是限制（预填充能跑 89~139 tok/s，说明算力大量富余）；
3. **等效位宽反而更大** —— NVFP4 = 4 bit + 分块缩放 ≈ 4.5 bpw，比现用主体的 3.57 bpw 更大，在这个"模型比总内存还大"的场景里等于每 token 多读 26% 的字节，只会更慢。

详细论证与数据见 [model-reference §2.4](./model-reference.md)。

## 三、引擎与运行时：两个"静默失败"的坑

### 坑 1：引擎必须原生支持 Blackwell（sm_120）

5090 是 sm_120 架构，老版 llama.cpp 的 CUDA 构建不含对应内核。选了 unslothai 的 `b10840-mix` 构建（`cuda12-portable` 变体，其 `supported_sms` 列表包含 120）。**验证方法**：用 `llama-bench --help` 确认有 `-ncmoe` 参数、查 `BUILD_INFO` 确认 sms 列表。

### 坑 2（最阴险）：所谓 "portable" 并不包含 CUDA 运行时

第一次跑基准，`llama-bench` 显示 `backend = CPU`——**没有任何报错**，推理静默跑在了 CPU 上。排查过程：

1. 用 `ctypes.WinDLL("ggml-cuda.dll")` 试加载，报"找不到依赖"；
2. 自写 PE 解析器读导入表，发现 `ggml-cuda.dll` 静态依赖 `cudart64_12.dll` 和 `cublas64_12.dll`——这两个 DLL **机器上不存在**；
3. 所谓 "portable" 只是把 CUDA **内核**（338 MB 的 `.nv_fatb` 段）嵌进了 DLL，运行时库仍需自备。

**解法**：不装几个 GB 的 CUDA Toolkit，直接从 PyPI 拉 NVIDIA 官方 Windows wheel（版本可精确对齐构建时的 12.8）：

```
nvidia-cuda-runtime-cu12==12.8.90  → cudart64_12.dll
nvidia-cublas-cu12==12.8.5.5       → cublas64_12.dll / cublasLt64_12.dll / nvblas64_12.dll
```

wheel 本质是 zip，解出 4 个 DLL 放进引擎目录即可。修复后验证：

```
ggml_cuda_init: found 1 CUDA devices:
  Device 0: NVIDIA GeForce RTX 5090 Laptop GPU, compute capability 12.0, VRAM: 24435 MiB
backend = CUDA
```

**教训二：显卡部署里最危险的不是报错，是"静默退回 CPU"。** 建议每次换引擎/换模型后，先用一个 1 MB 的迷你模型跑 `llama-bench`，确认输出里有 `backend = CUDA` 和 `compute capability`，再谈其他。

## 四、下载：镜像限流的应对

模型总量 88 GiB，走 hf-mirror。实测它有**滚动令牌桶限流**：连续下载 2~4 GB 后速度归零（0.03~0.5 MB/s），静置 5~10 分钟自行恢复，恢复后单连接 14.5 MB/s、多连接 20~26 MB/s。对照组测试（GitHub 加速代理恒定 26 MB/s）证明是站点限流而非本机网络。

应对：

- 自写多线程分块下载器：**固定 256 MiB 块大小**（与线程数无关，避免换线程数续传时块边界错位写坏文件）、断点续传、失败无限重试+指数退避（封顶 60 秒）；
- ModelScope 有同仓库镜像，但实测更慢（多线程仅 1.3 MB/s），弃用；
- 下载完成后用 HuggingFace 的 LFS sha256 逐文件校验（注意 API 字段是 `lfs.sha256`，请求需带浏览器 UA 否则 403）。

33 个分片全部校验通过，一个字节不差。

## 五、调优实战：`--n-cpu-moe` 扫描与一次惨痛的数据污染

### 5.1 核心旋钮：`--n-cpu-moe N`（前 N 层的专家权重留在 CPU）

用 `llama-bench` 扫描（`-ngl 99 -fa on -p 512 -n 128`）：

| ncmoe | 显存里的专家层数 | pp512 | **tg128（生成）** |
|---|---|---|---|
| 44 | 4 | 53.5 | 22.57 |
| 40 | 8 | 92.3 | 24.99 |
| 36 | 12 | 79.4 | 17.78 |
| 34 | 14 | 60.2 | 24.89 |
| **32** | 16 | 55.7 | **26.88 ← 最优** |
| 28 | 20 | 20.6 | **4.65 ← 悬崖** |

28 层时显存溢出，驱动**静默**把溢出部分搬进内存走 PCIe——速度直接塌方。这条曲线的形状（平缓下降 + 突然悬崖）是所有显存分层的典型特征。

### 5.2 惨痛教训：进程泄漏污染了整轮数据

调参中期出现过大量"莫名其妙的慢"：MTP 掉到 1.2 tok/s、16K 上下文掉到 1.4 tok/s……排查到最后发现根因是**脚本里杀进程的命令静默失效**（Git Bash 的参数转换问题），llama-server 实例越攒越多，最多时 4 个并存——每个实例都要 13~16 GiB 显存，叠加起来显存溢出、内存冲到 99%，所有当轮数据全部作废。

修复后的**单实例测试纪律**（固化成了一个 Python 测试驱动）：

1. 杀进程用 Python `subprocess` 参数数组调 `taskkill`（绕开 shell 转义），杀完用 `tasklist` **验证清零**；
2. 每组测试独立进程，启动 → 就绪 → 预热 2 次 → 测量 → 杀净 → 验证；
3. 全程每秒采样内存占用，按案例时间窗统计峰值；
4. 数据以"热态"（预填充/预热完成后的稳态）为准，冷启动第一发普遍偏低。

### 5.3 内存机制实测：mmap 工作集 > 物理内存是天性，不是故障

修复后重新采样，健康配置的内存曲线是：

```
空闲        52.6 GiB 空闲 (17%)
模型加载 →  30.9 GiB 空闲 (51%)   ← 32 层专家进内存
生成过程 →  12.3 GiB 空闲 (80%)   ← mmap 页缓存增长（可回收，但占水位）
稳态     →   9.5 GiB 空闲 (85%)   ← 健康态就这样
```

**mmap 映射工作集 67.4 GiB > 物理内存 64 GiB 是这套方案的天然属性**（"表放 SSD"的前提），操作系统靠淘汰冷页维持。单实例下内存峰值稳定在 82~96%，从不失控；**所有"内存爆到 99%"都来自多实例叠加**。

两个配套的保险丝（强烈建议设置）：

1. **NVIDIA「CUDA - 系统内存回退策略」→ 首选无系统内存回退**：默认策略下显存溢出会静默搬进内存走 PCIe（慢 30 倍、无报错）；改后直接报 OOM，把"看不见的失败"变成"看得见的失败"；
2. **页面文件加大**（9 GiB → 32~64 GiB）：提交上限 = 内存 + 页面文件，给尖峰留缓冲。

## 六、MTP 投机解码：机制性负收益，放弃

模型自带 MTP 投机解码头（shared 版 2.60 GiB / 自包含版 3.85 GiB），官方场景下号称 1.3~1.7x 加速。实测（单实例干净环境，draft 接受率 50~63%，确认真实在工作）：

| ctx | 无 MTP | MTP (ncmoe=35) |
|---|---|---|
| 8192 | 20.08 | 21.44（shared）/ 18.37（自包含）/ 19.20（自包含+强制进显存） |
| 32768 | 21.66 | 14.55 |

**8K 下打平，32K 下反慢 33%。** 原因是机制性的：MoE 模型下投机解码的验证批要一次前向 3 个 token，激活专家是 3 个 token 的**并集**——每步验证从内存读 2~3 倍的专家权重，除以 2.1 的接受率，每 token 流量反而放大 1.4~3 倍。**MTP 的正收益只存在于"专家全部驻留显存"的场景**（那时权重读取不随批量增加）；官方的加速数据就来自那种 128 GB 大内存全装下的配置。

结论：在"专家大部分驻留内存"的分层路线上，MTP 是负收益，果断关闭。换成自包含头、用 `-ot` 强制把 draft 头专家压进显存，都试过，无改善。

## 七、长上下文突破：把显存还给 KV

### 7.1 一个反直觉的事实：KV 缓存小得出奇

verbose 日志抓到的显存账本（ncmoe=32, ctx=8192）：

| 显存项 | 大小 |
|---|---|
| 模型权重（16 层专家 + 注意力 + embedding） | 20.87 GiB |
| **KV 缓存** | **0.26 GiB** |
| RS 缓存（GatedDeltaNet 循环态，**固定不随 ctx 涨**） | 0.11 GiB |
| 计算缓冲 | 0.64 GiB |

这个模型只有 **2 个 KV 头**（GQA 极致版）+ 大部分层是固定状态的 GatedDeltaNet——每 token 的 KV 增量仅 **33 KiB**。256K 全长上下文的 KV 也不过 8.25 GiB。

**上下文短的瓶颈从来不是 KV，而是"显存被专家占了"。** 那么解法就清晰了：每把 2 层专家从显存挪回内存（腾 2.06 GiB），上下文就能翻一倍。

### 7.2 跷跷板实测：一路推到 256K 全长

| 配置 | 上下文 | ncmoe | 生成速度 | 8K 长文预填充后 | RAM 峰值 |
|---|---|---|---|---|---|
| 基准 | 32K | 32 | 21.66 | — | 83% |
| C3 | **64K** | 34 | 24.61 | **26.88**（1 万 token 预填充 139 t/s） | 96% |
| **C2b** | **256K 全长** | **42** | **23.43** | **22.81**（预填充 111 t/s） | 95% |
| C1 | 256K 全长 | 48（全部专家进内存） | 17.67 | 22.50（预填充 89 t/s） | 94% |

三个要点：

1. **256K（模型标称全长）实测可用，速度与 32K 持平甚至更快**——"稀疏注意力 + DeltaNet 混合架构"的长上下文优势被三层分配完全释放；
2. **大 KV 建立后生成速度不掉**（预填充 1 万 token 只需 ~90 秒）；
3. 256K 时预填充计算缓冲要 1.98 GiB，会吃掉一个配置档（ncmoe=40 直接 OOM，42 可行）——**上下文每上一个台阶，要同步检查计算缓冲**。

### 7.3 最终前沿（速度 ↔ 上下文，实测）

| 需求 | 配置 | 实测 |
|---|---|---|
| 极速档 | ncmoe=34, ctx=64K | 24.6~28.2 tok/s |
| **均衡档（定稿）** | **ncmoe=42, ctx=256K 全长** | **22.8~23.4 tok/s** |
| 多会话档 | ncmoe=48, ctx=256K | 17.7~22.5 tok/s，显存余 8.4 GiB 可开多槽 |

跷跷板规律：**每 +2 层专家回内存 ≈ 腾 2.06 GiB 显存 ≈ 上下文翻一倍**，且在整条曲线上速度衰减平缓（因为速度瓶颈在"每 token 读多少专家字节"，而挪层只是换存储位置）。

## 八、3.84bpw 对照：速度 +5~9.5%，质量留白

主体小 17% 的 AD-3.84（79.10 GiB / 28 片，sha256 全过）做了同口径对照：

| 配置 | 3.84 | 4.27 | 差 |
|---|---|---|---|
| ncmoe=34, ctx=64K | 25.59（大 KV 后 **28.24**） | 26.88（大 KV 后） | **+5%** |
| ncmoe=42, ctx=256K | 18.66（大 KV 后 **24.97**） | 23.43 / 22.81 | **+9.5%** |

热态对比 3.84 快 5~9.5%——方向对，但低于理论 17%，说明瓶颈是"专家字节 + 内存带宽 + 缺页率"的混合。附带红利：主体更小，显存余量更大（4.27 在 ncmoe=40 配 256K 会 OOM，3.84 不会）。

**但主体 ≈2.92bpw 的质量没有任何公开数据背书**。笔者的做法：两版并存，拿日常任务各跑几天再定主力；对质量敏感的场景默认 4.27。

## 十、可复用的经验清单

1. **布局 > 位宽**：模型比内存大时，先看 GGUF 分片结构（大权重表是否独占分片），再谈量化档位；
2. **警惕两类静默失败**：CUDA 运行时缺失 → 静默退回 CPU；显存溢出 → 静默走 PCIe。对策：迷你模型验证 `backend=CUDA` + 驱动设「无系统内存回退」让溢出显式报错；
3. **MoE + CPU 专家 = 投机解码负收益**：验证批的专家激活并集会放大内存流量，MTP/draft 只适合全显存场景；
4. **KV 远比你想象的小**：GQA + 混合注意力架构（固定循环态）下，上下文的成本趋近于零——显存应该尽量让给 KV；
5. **跷跷板公式**：每 2 层专家在显存/内存间挪动 ≈ 1 GiB ≈ 上下文 32K 容量，可以精确规划 (ncmoe, ctx) 组合；
6. **数据卫生**：多实例泄漏会让一整轮基准全部作废——起停必须验证进程清零，基准驱动固化成脚本，只信热态数据；
7. **镜像限流是常态**：分块断点续传 + 无限重试 + 长退避，比换源更可靠（至少对 hf-mirror）；
8. **sha256 校验不可省**：浏览器/下载工具改文件名、分片缺一不可察觉，HF 的 LFS 哈希是免费的真相源。
