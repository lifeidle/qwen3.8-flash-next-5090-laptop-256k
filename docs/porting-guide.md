# 移植指南：把这套配方搬到其他硬件 / Porting Guide

> 公式与对照表：算出你自己机器上的 `--n-cpu-moe` 与上下文长度。
> Formulas and a lookup table for sizing `--n-cpu-moe` and context on your own machine.

---

## 1. 三个约束 / Three constraints

部署"模型总量 > 显存 + 内存"的大模型，是在三个约束下做取舍：

| 约束 | 限制什么 | 关键公式 |
|---|---|---|
| **显存** | 上下文长度 | `VRAM 占用 = 常驻 + 专家 + KV + 计算缓冲 + 循环态` |
| **内存** | 能留多少层专家在 CPU | `RAM 工作集 ≈ ncmoe × 单层专家字节 + N-gram 表` |
| **带宽** | 生成速度 | 每 token 读 `ncmoe × 单层激活专家字节`，实测约 20~25 GB/s 为上限 |

## 2. 显存公式（以本模型 AD-4.27bpw 为例）/ VRAM formula

```
VRAM ≈ 4.4 GiB (注意力/常驻张量)
     + (48 − ncmoe) × 1.03 GiB      ← 单层专家字节（3.84 档为 0.89）
     + ctx × 33 KiB / 1024² × KT    ← KV 缓存；KT = KV 量化系数
                                        f16 = 1.00，q8_0 ≈ 0.50，q4_0 ≈ 0.25
     + 计算缓冲                      ← 8K ≈ 0.64 GiB，256K ≈ 1.98 GiB（线性插值）
     + 0.11 GiB (GatedDeltaNet 循环态，固定)

可用显存 ≈ 显卡标称 − 1.3 GiB（桌面/系统占用）
```

> 💡 **两条免费的提速思路**（都不改量化精度）：
> ① **KV 量化换专家层**：256K 下 KV 用 q8_0 可省 4.12 GiB ≈ 4 层专家进显存 → 实测 **+3.4~5%**，长上下文召回精度无损失（见 `results/needle-accuracy.txt`）；
> ② **别贴着显存上限配**：留 1.5 GiB 以上余量，临界值会随机 OOM。

**校验**：本机 24 GB 卡（24435 MiB 可见，可用 ≈23.1 GiB）

| ncmoe | ctx | 公式计算 | 实测结果 |
|---|---|---|---|
| 32 | 8192 | 21.9 GiB | ✅ 通过（20.1~21.7 tok/s） |
| 34 | 65536 | 22.0 GiB | ✅ 通过（24.6~28.2 tok/s） |
| **38** | **262144** | *19.0 GiB（KT=0.5）* | ✅ **通过（中位数 22.07 tok/s）← 定稿（KV=q8_0）** |
| 42 | 262144 | 20.9 GiB | ✅ 通过（中位数 21.34 tok/s，KV=f16） |
| 40 | 262144 | 23.0 GiB | ❌ 实测 OOM |
| 34 | 262144 | 26.8 GiB | ⚠️ 公式超限（未实测） |

> ⚠️ 两条经验：
> ① **不要贴着上限配**——公式结果与可用显存差距 < 1 GiB 时，桌面占用一波动就随机 OOM，建议留 **1.5 GiB** 余量；
> ② **`可用显存 = 显卡标称 − 桌面占用`**，本文用的 1.3 GiB 是实测值。若后台常开浏览器硬件加速、录屏、游戏启动器，这个数字会更大，需相应上调 ncmoe。

## 3. 内存公式 / RAM formula

```
RAM 工作集 ≈ ncmoe × 1.03 GiB (CPU 端专家) + 35.76 GiB (N-gram 表, mmap)
```

要点：**N-gram 表是 mmap 映射，不计入"必须常驻"**——表页由 OS 按需缓存/淘汰，所以工作集略超物理内存是可以的。实测三档：

| ncmoe | CPU 专家 | 表（mmap） | 工作集合计 | 比值 | 实测表现 |
|---|---|---|---|---|---|
| 32 | 33.0 GiB | 35.76 GiB | 68.8 GiB | /64 = **1.07** | ✅ 内存峰值 83%，稳定 |
| 42 | 43.3 GiB | 35.76 GiB | 79.0 GiB | /64 = **1.23** | ✅ 内存峰值 95%，稳定（256K 档） |
| 48 | 49.4 GiB | 35.76 GiB | 85.2 GiB | /64 = **1.33** | ✅ 内存峰值 94%，稳定（但速度降到 17.7~22.5，因为读专家变多） |

**结论**：比值 **≤1.35 有实测支撑**（1.07 / 1.23 / 1.33 三档都稳定跑通）。超过 1.4 **未验证**——理论上表页可回收，但缺页率会上升。注意：速度下降的主因是**每 token 读的专家字节变多**，不是页面交换。

**前提**：模型必须是 **M64 类布局**（N-gram 表独占分片）。混装布局会把「表 + 同片专家」整片锁定、无法换出，工作集直接爆掉（见 model-reference §2.3）。

## 4. 硬件对照表 / Hardware lookup

| 显存 | 内存 | 推荐 ncmoe | 上下文 | 生成速度 | 依据 |
|---|---|---|---|---|---|
| **24 GB（本机）** | **64 GB** | **38**（KV=q8_0） | **256K 全长** | **22.1~25.3 tok/s** | ✅ 实测 · **定稿** |
| 24 GB（本机） | 64 GB | 42（KV=f16） | 256K 全长 | 21.3 tok/s | ✅ 实测 · 关 KV 量化的基线 |
| 24 GB（本机） | 64 GB | 32（KV=f16） | 64K | 24.6~28.2 tok/s | ✅ 实测 · 速度档 |
| 24 GB | 96 GB | 34~36（KV=q8_0） | 256K | 25~28 tok/s | ⚠️ 推算（内存宽裕，专家可多留几层在显存） |
| 32 GB（台式 5090） | 64 GB | 30~32（KV=q8_0） | 256K | 26~30 tok/s | ⚠️ 推算（显存多 8 GiB ≈ 多放 8 层专家） |
| 48 GB | 96 GB | 18~22（KV=q8_0） | 256K | 30+ tok/s | ⚠️ 推算（大部分专家可进显存） |
| 16 GB | 64 GB | 40~42（KV=q8_0） | 64K~128K | 14~18 tok/s | ⚠️ 推算（显存更紧，建议配 AD-3.84 档） |
| 16 GB | 32 GB | 44（KV=q8_0） | 16K~32K | 10~14 tok/s | ⚠️ 推算（内存也紧张，优先 3.84bpw 档） |

> **只有前 3 行是实测**（本机 24 GB + 64 GB）；其余为公式推导外推，**未实测**。
> 表中非本机行按 **KV=q8_0** 给出（省下的 KV 显存可多放约 4 层专家）；若用 f16 KV，ncmoe 需 +4。

## 5. 五步自查清单 / Five-step checklist

1. **两侧分别算账，都别越界**：
   - 显存侧 = 注意力常驻 + (48−ncmoe)×单层专家 + KV + 计算缓冲 + 循环态 ≤ 可用显存 − 1.5 GiB；
   - 内存侧 = ncmoe×单层专家 + 表映射，比值 ≤ 1.35；
2. **分片布局**：N-gram 表（本模型 35.76 GiB）是否独占分片？
3. **引擎可用性**：迷你模型跑 `llama-bench`，输出含 `backend = CUDA` + 正确的 compute capability？
4. **先跑通再压测**：用最保守组合（ncmoe=48 + ctx=8192）确认能启动、能出字，再逐档往上试；
5. **内存纪律**：每次启动前确认**没有残留的 llama-server 进程**。

## 6. 调参顺序建议 / Suggested order

```
1. 保守起步：ncmoe = 48（全部专家在内存）+ ctx = 8192      → 确认能跑通
2. 找速度甜点：ncmoe 从 44 往下扫（44/40/36/34/32/28）      → 出现悬崖就停
3. 换上下文：按公式把 ctx 拉到 32K/64K/128K/256K             → 越界即 OOM
4. 平衡两者：每 +2 层专家回内存 ≈ 腾 2.06 GiB ≈ ctx 翻倍
5. 固化：把最优组合写进启动脚本
```

工具 / Tools：
- `tools/bench_single_instance.py` —— ncmoe 扫描（单实例纪律 + 内存采样）
- `tools/ab_bench.py` —— 多轮取中位数的服务端 A/B（**单发测量不可靠**）
- `tools/needle_test.py` —— 长上下文召回精度测试（多组随机化大海捞针）

```bash
# 1) 扫描 ncmoe 找速度甜点
python bench_single_instance.py --server <llama-server> --model <首分片.gguf> \
    --configs "44:8192,40:8192,34:65536,38:262144" --long-tokens 8000

# 2) 生产配置多轮基准（中位数）
python ab_bench.py --server <llama-server> --model <首分片.gguf> \
    --ncmoe 38 --ctx 262144 --rounds 6 --extra "-ctk q8_0 -ctv q8_0" --long-test

# 3) 精度验证（改了 KV 量化/上下文后必跑）
python needle_test.py --server <llama-server> --model <首分片.gguf> \
    --ncmoe 38 --ctx 262144 --trials 4 --extra "-ctk q8_0 -ctv q8_0"
```
