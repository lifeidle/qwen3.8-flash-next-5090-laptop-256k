# 移植指南：把这套配方搬到其他硬件 / Porting Guide

> 本页给出**可计算**的推算公式与配置对照，让你在自己机器上直接算出该用多少 `--n-cpu-moe`、上下文能开多大。
> This page gives the formulas and a lookup table so you can size `--n-cpu-moe` and context for your own machine.

---

## 1. 三个约束 / Three constraints

部署这种"模型总量 > 显存 + 内存"的大模型，本质是在三个约束下做取舍：

| 约束 | 限制什么 | 关键公式 |
|---|---|---|
| **显存** | 上下文长度 | `VRAM 占用 = 常驻 + 专家 + KV + 计算缓冲 + 循环态` |
| **内存** | 能留多少层专家在 CPU | `RAM 工作集 ≈ ncmoe × 单层专家字节 + N-gram 表` |
| **带宽** | 生成速度 | 每 token 读 `ncmoe × 单层激活专家字节`，实测约 20~25 GB/s 为上限 |

## 2. 显存公式（以本模型 AD-4.27bpw 为例）/ VRAM formula

```
VRAM ≈ 4.4 GiB (注意力/常驻张量)
     + (48 − ncmoe) × 1.03 GiB      ← 单层专家字节（3.84 档为 0.89）
     + ctx × 33 KiB / 1024²         ← KV 缓存
     + 计算缓冲                      ← 8K ≈ 0.64 GiB，256K ≈ 1.98 GiB（线性插值）
     + 0.11 GiB (GatedDeltaNet 循环态，固定)

可用显存 ≈ 显卡标称 − 1.3 GiB（桌面/系统占用）
```

**校验**：本机 24 GB 卡（可用 23.1 GiB）

| ncmoe | ctx | 公式结果 | 实测 |
|---|---|---|---|
| 32 | 8192 | 21.9 GiB | ✅ 通过（20.1~21.7 tok/s） |
| 34 | 65536 | 22.0 GiB | ✅ 通过（24.6~28.2 tok/s） |
| 34 | 262144 | 26.8 GiB | ❌ 超限 |
| 40 | 262144 | 23.0 GiB | ❌ 实测 OOM（临界值不可信） |
| **42** | **262144** | **20.9 GiB** | ✅ 通过（22.8~23.4 tok/s） |

> ⚠️ 经验：**不要贴着上限配**。临界值（差距 < 0.5 GiB）在桌面占用波动时会随机 OOM，留 1.5 GiB 以上余量。

## 3. 内存公式 / RAM formula

```
RAM 工作集 ≈ ncmoe × 1.03 GiB (CPU 端专家) + 35.76 GiB (N-gram 表, mmap)
```

要点：**N-gram 表是 mmap 映射，不计入"必须常驻"**——真正要常驻的是 CPU 专家。表的页由 OS 按需缓存/淘汰，所以：

- 工作集 / 物理内存 ≤ 1.35 → 稳定（本机 ncmoe=42：79 / 64 = 1.23 ✅）
- 比值 1.35~1.45 → 能跑但缺页增多、速度下滑（本机 ncmoe=48：85 / 64 = 1.33，实测 17.7 冷 / 22.5 热）
- 比值 > 1.5 → 页面风暴风险

**前提**：模型必须是 **M64 类布局**（N-gram 表独占分片）。若用混装布局，「表 + 同片专家」会被整片锁定，工作集直接爆掉（详见 model-reference §2.3）。

## 4. 硬件对照表 / Hardware lookup

| 显存 | 内存 | 推荐 ncmoe | 上下文 | 预期生成速度 | 说明 |
|---|---|---|---|---|---|
| **24 GB**（本机） | **64 GB** | **42** | **256K 全长** | **23.4 tok/s** | 均衡档 |
| 24 GB | 64 GB | 34 | 64K | 24.6~28.2 tok/s | 速度档 |
| 24 GB | 64 GB | 48 | 256K | 17.7~22.5 tok/s | 显存余 8.4 GiB，可开 `-np` 多会话 |
| 24 GB | 96 GB | 38~40 | 256K | 25~28 tok/s（预估） | 内存更宽裕，专家可多留几层在显存 |
| 16 GB | 64 GB | 44~46 | 64K~128K | 14~18 tok/s（预估） | 显存更紧，建议配 AD-3.84 档 |
| 16 GB | 32 GB | 48 | 16K~32K | 10~14 tok/s（预估） | 内存也紧张，优先 3.84bpw 档 |
| 32 GB（台式 5090） | 64 GB | 34~36 | 256K | 26~30 tok/s（预估） | 显存多 8 GiB ≈ 多放 8 层专家 |
| 48 GB | 96 GB | 22~26 | 256K | 30+ tok/s（预估） | 大部分专家可进显存 |

> 「预估」= 用第 2 节公式推导 + 本机实测速度曲线外推，未实测。**实测列可信，预估列仅作规划参考。**

## 5. 五步自查清单 / Five-step checklist

1. **模型总量 vs 显存+内存**：`模型 GiB ≤ 显存 + 内存 × 0.85`？
2. **分片布局**：大权重表（本模型 N-gram 表 35.76 GiB）是否独占分片？（混装布局直接放弃）
3. **引擎可用性**：迷你模型跑 `llama-bench`，输出含 `backend = CUDA` + 正确的 compute capability？
4. **显存预算**：套第 2 节公式，留 1.5 GiB 余量，先用保守档跑通，再逐档压测；
5. **内存纪律**：每次启动前确认**没有残留的 llama-server 进程**（多实例是本项目踩过的最大坑）。

## 6. 调参顺序建议 / Suggested order

```
1. 保守起步：ncmoe = 48（全部专家在内存）+ ctx = 8192      → 确认能跑通
2. 找速度甜点：ncmoe 从 44 往下扫（44/40/36/34/32/28）      → 出现悬崖就停
3. 换上下文：按公式把 ctx 拉到 32K/64K/128K/256K             → 越界即 OOM
4. 平衡两者：每 +2 层专家回内存 ≈ 腾 2.06 GiB ≈ ctx 翻倍
5. 固化：把最优组合写进启动脚本
```

工具：本仓库 [`tools/bench_single_instance.py`](../tools/bench_single_instance.py) 可直接跑这套流程（含单实例纪律与内存采样）。

```bash
python bench_single_instance.py \
  --server /path/to/llama-server \
  --model  /path/to/model-00001-of-000NN.gguf \
  --configs "44:8192,40:8192,34:65536,42:262144" \
  --long-tokens 8000
```
